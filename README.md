# Sahaay — Offline-First Cognitive Care for Dementia Patients

**SIH 2026 · Problem Statement SIH26003 · North Eastern Region**

Sahaay is a Progressive Web App that helps elderly patients with dementia maintain cognitive function through four adaptive mini-games, while giving their caregivers and doctors a real-time clinical window into progress. It is built to work in low-connectivity areas — the games never touch the network during play.

---

## The problem it solves

Dementia care in the North Eastern Region means patchy connectivity, shared devices, and patients who cannot be expected to remember passwords or wait for a spinner. Existing tools assume always-on internet and technically literate users. Sahaay does not.

The app adapts game difficulty based on how the patient actually performed — not just today, but over weeks — and surfaces that analysis to the doctor without requiring a network call on every page load.

---

## What it does

**For the patient**
Four cognitive mini-games, each targeting a different domain:

| Game | Domain | What it trains |
|---|---|---|
| Memory Matching | Memory | Recall — pairs of cards, increasing grid size |
| Daily Routine | Routine | Sequencing — reorder the steps of a daily task |
| Object Recognition | Recognition | Naming — identify household objects from images |
| Name Recall | Memory | Recall — match a face to a name from their life |

Difficulty adjusts automatically after each round. The AI writes a plan in advance; the game reads from that plan offline, with no network needed. A result screen shows a warm, plain-language reason for the adjustment ("We'll try a little more next time"), spoken aloud in the patient's language and accompanied by a badge indicating whether the guidance came from the AI plan or the offline rule engine.

A personal Memory Vault lets caregivers store the people, photos, and routines that matter to the patient — used directly by the Name Recall game.

**For the caregiver**
- Dashboard showing the patient's recent sessions, domain scores, adherence to reminders, and current difficulty level
- Reminder management (medicine, hydration, appointments)
- On-demand progress reports generated by the AI — two tones: family-warm (caregiver) and clinical (doctor)
- Offline indicator showing when the device last synced

**For the doctor**
- Dashboard over their full caseload — smart patient cards ranked by risk, a priority strip highlighting who needs attention first, and an AI Clinical Assistant sidebar
- Per-patient clinical view: 30-day trend graph, domain breakdown, difficulty history with AI reasoning, clinical notes, recommended actions, percentile against their own cohort
- Generate a weekly clinical report per patient on demand

## Architecture in one paragraph

The frontend (React + Vite + Dexie) runs offline-first. Game sessions are queued in IndexedDB and synced to the FastAPI backend when connectivity returns. The Cognitive Coach — a LangChain chain backed by Groq (Llama 3.1) or Gemini — reads those sessions server-side and writes a multi-branch difficulty plan back to the device. The plan covers every possible outcome of the next round, so the game adapts with no network at all. A deterministic rule engine serves as the safety floor when no plan has been cached. The Report Generator chain produces structured four-section reports, persisted to SQLite so the doctor dashboard never triggers a model call on page load.

```
Patient plays a round
       │
       ▼
IndexedDB (instant)  ◄── Cached AI plan (3 branches: good / ok / poor)
Result shown immediately + reason spoken aloud
       │
       ▼ (background, when online)
FastAPI ──► Cognitive Coach ──► Fresh plan ──► IndexedDB
```

## Data model

Seven server-side tables:

- **users** — all three roles (patient · caregiver · doctor) in one table with a `role` column
- **patients** — linked to a caregiver (1:1, unique FK) and a doctor (1:many); carries `age`, `diagnosis_stage`, `preferred_language`, `last_sync_at`
- **game_sessions** — every completed or abandoned round; `domain` resolved at write time from `game_type`
- **difficulty_history** — every difficulty change with `from_level`, `to_level`, `reason`, and `source` (rule or ai)
- **clinical_notes** — doctor-written notes plus AI-generated summary
- **ai_reports** — persisted report JSON (four sections); never regenerated on dashboard load
- **reminder_logs** — every reminder firing with `status` (done / missed / pending); the only source for adherence %

Client-side (Dexie v3):

- **aiPlans** — cached multi-branch difficulty plans keyed by `[patientId+gameType]`
- **gameSessions** — offline queue; synced via `/sessions/sync`
- **patients** — local profiles with `serverId` for the device ↔ server identity map

## How the adaptive difficulty works

The game loop reads from a cached plan — always, online and offline alike:

```js
// Every plan covers three outcomes for every game
{
  patientId: 3,
  gameType: "memory",
  currentLevel: 3,
  generatedAt: "2026-08-27T09:14:00Z",
  source: "ai",              // "rule" when the LLM was not available
  ifGood: { level: 4, reason: "Doing beautifully — let's try a little more." },
  ifOk:   { level: 3, reason: "Steady and consistent — same level next time." },
  ifPoor: { level: 2, reason: "We'll take it a little gentler next time." }
}
```

After a round ends, the app classifies the outcome (`good` / `ok` / `poor`) from accuracy or move ratio, picks the matching branch, and applies a ±1 clamp. The result is shown on screen and spoken aloud via TTS in the patient's preferred language. A background task then syncs the session and fetches a fresh plan for next time.

**Staleness rules:** Plans older than 7 days, or used for 10+ rounds without refresh, fall back to the deterministic rule engine until connectivity returns.

**Mode indicator:** Every result screen shows a `SourceBadge` — "Updated by AI" when the cached plan is fresh, "Saved guidance" when the rule engine took over. The offline fallback is visible, not hidden.

## Multilingual and cultural support

The patient-facing interface supports English (`en`) and Assamese (`as`) — the primary language of the North Eastern Region. Language is stored per user (`preferred_language` on the `users` table) and applied automatically on login.

When `preferred_language` is set to `as`:
- All patient home screen strings render in Assamese
- The voice greeting TTS fires in Assamese (`as-IN` locale)
- The AI-written reason after each game round is spoken aloud in Assamese
- The Memory Vault voice Q&A listens and responds in Assamese

The `i18n.js` module exposes a `useT()` hook and a `langToLocale()` helper. Caregiver and doctor surfaces remain in English.

**NER-cultural game content:** The games include objects and references familiar to elderly patients in Assam and the wider NER — bamboo, tea, paddy, diya, elephant, parrot, mustard oil, and traditional baskets appear in Object Recognition and Memory Matching. Name Recall uses common Assamese surnames (Hazarika, Bora, Kalita, Das) alongside pan-Indian names.

## Running locally

### Backend

```bash
cd backend

# Create .env with the required variables
cat > .env << 'EOF'
SECRET_KEY=your-secret-key-min-32-chars
GROQ_API_KEY=your-groq-key          # optional — app runs without it
GEMINI_API_KEY=your-gemini-key      # optional fallback
EOF

pip install -r requirements.txt

# First run — create tables and seed demo data
python rebuild_db.py --seed

# Start the API
uvicorn app.main:app --reload
```

API is live at `http://localhost:8000`. Interactive docs at `/docs`.

### Frontend

```bash
cd frontend
npm install
npm run dev
```

App is live at `http://localhost:5173`.

## The three-role access model

```
Doctor (1) ──── assigns ────► Patient (many)
                                    │
Caregiver (1) ─── cares for ────────┘ (unique FK — one caregiver per patient)
```

Every endpoint calls `resolve_patient_access(user, patient_id)`, which returns the patient only if the requesting user's role grants them access. 404 is returned instead of 403 on access denial — a caregiver probing IDs should not learn which patient IDs exist.

Patient-side routes are intentionally unguarded: a patient with dementia cannot be expected to recall a password. The security boundary for patient data is the server's role checks on all caregiver and doctor endpoints.

## Offline strategy summary

| Capability | Online | Offline |
|---|---|---|
| Play all four games | ✓ | ✓ |
| Adaptive difficulty | ✓ (AI plan) | ✓ (cached plan or rule engine) |
| AI-written reasons | ✓ | ✓ (from cached plan) |
| Voice feedback after round | ✓ | ✓ (spoken from cached plan) |
| Session logging | ✓ | ✓ (queued in IndexedDB) |
| Session sync | ✓ | — (queued until next connection) |
| Caregiver dashboard | ✓ | Partial (local data only) |
| Doctor dashboard | ✓ | — (requires server) |
| Generate reports | ✓ | — (requires LLM) |

The app shell is pre-cached by the PWA service worker. After the first load, the patient-facing half works with no internet at all.

## The AI layer — what it actually is

The pitch calls these "agents." They are LangChain chains:

```
ChatPromptTemplate | LLM | PydanticOutputParser | OutputFixingParser
```

`OutputFixingParser` catches fenced or chatty LLM replies and self-corrects them instead of returning a 502. The result is always a typed Pydantic model, not raw JSON.

The doctor dashboard uses no LLM on page load. Trend direction, domain scores, risk bands, and the priority strip are computed by `analytics.py` — pure Python, deterministic, fast. The LLM writes the reasons and report text, which are stored and read from `ai_reports`. Loading 15 patient cards does not trigger 15 model calls.
